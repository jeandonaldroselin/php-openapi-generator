# Jean-Donald Roselin's PHP Openapi Generator

Composer package that generates PHP API clients from OpenAPI specs (via
[openapi-generator](https://openapi-generator.tech)) and makes them autoloadable directly from
your project — no separate `vendor/` package involved.

Running `generate-client`, for every client in the config:

1. Downloads (and caches) the right version of `openapi-generator-cli.jar`.
2. Runs it to generate the PHP client from your OpenAPI spec, into
   `var/openapi-generator/generated/<name>/`.
3. Adds a PSR-4 mapping for the client's namespace directly to your project's own
   `composer.json` (`autoload.psr-4`), pointing at that directory.

Then, once — after every client has been processed, not per client — it registers a
`post-install-cmd`/`post-update-cmd` script (if not already present) and runs a single `composer
dump-autoload --optimize` for the whole batch.

## Why not install into vendor/?

An earlier version of this tool installed each client as a real `vendor/<vendor>/<project>`
package, via a Composer `path` repository. That looks nice, but breaks on a **completely fresh
checkout**: a `path` repository requires its source directory to exist before Composer can
install it, and that directory (`var/openapi-generator/generated/...`) is generated by this very
tool — which itself needs to be installed first. There is no way to make a plain `composer
install` succeed from scratch with that design (a Composer plugin can't help either: plugins
only activate once already present in `vendor/`, so they can't intervene during their own first
installation).

Registering a PSR-4 mapping directly on the *consuming* project's `composer.json`, combined with
a `post-install-cmd`/`post-update-cmd` script, sidesteps the problem entirely: Composer doesn't
need the target directory to exist to record an autoload mapping, and root-project scripts run
reliably on every install, including the very first one (as long as there's at least one real
dependency to install, which is true in practice). By the time any application code actually
tries to use the generated classes, the script has already regenerated them.

## Requirements

- PHP 8.1+ and Composer, in the project you're generating clients for.
- A Java runtime (11+) available on the `PATH` (or configured via `java_binary`) — required
  by `openapi-generator-cli.jar` itself. Needed wherever `composer install`/`update` runs for
  this project (including CI and Docker builds), since that's what triggers generation.

## Installation

```bash
composer require --dev jeandonaldroselin/php-openapi-generator
```

## 1. Configure the client(s) to generate

Create `openapi-generator.json` at the root of your project (copy
`vendor/jeandonaldroselin/php-openapi-generator/config/openapi-generator.dist.json` as a starting point):

```json
{
    "clients": [
        {
            "name": "billing",
            "input_spec": "https://api.example.com/openapi.yaml",
            "generator_name": "php",
            "package_name": "acme/billing-client",
            "openapi_generator_version": "7.9.0",
            "additional_properties": {
                "invokerPackage": "Acme\\Billing\\Client"
            }
        }
    ]
}
```

A single client can also be declared without the `clients` wrapper (top-level object = one client).

| Key                          | Required | Description                                                        |
|-------------------------------|----------|----------------------------------------------------------------------|
| `name`                       | yes      | Identifier, used for `--client` filtering and the output subfolder.  |
| `input_spec`                 | yes      | Path or URL to the OpenAPI spec.                                     |
| `package_name`                | yes      | Cosmetic identifier written into the generated composer.json's `name` field (`vendor/project` form). Not installed as a real dependency. |
| `generator_name`              | no       | openapi-generator generator, default `php`.                          |
| `openapi_generator_version`   | no       | Overrides the default generator version for this client.             |
| `additional_properties`       | no       | Passed as `--additional-properties` to the generator. `invokerPackage` determines the PHP namespace that gets autoloaded. |
| `global_properties`           | no       | Passed as `--global-property` to the generator.                      |
| `package_version`             | no       | Version written to the generated composer.json. Defaults to the spec's `info.version` (for a local file), else `1.0.0`. |

## Generated composer.json

The `name` (cosmetic) and `version` fields are filled in automatically since not every
openapi-generator template sets them. This file is never installed as a dependency — it exists
purely for documentation/tooling that inspects the generated directory.

## Skipping unchanged specs

Every generated client stores a parsed snapshot of the OpenAPI spec that produced it, at
`.openapi-generator/source-spec.json` inside the generated directory. On the next run, the
current `input_spec` is parsed and compared against that snapshot: if nothing functionally
changed (only comments, formatting, or key order differ), generation is skipped and the code
already in `var/` is left as-is. Use `--force` (`-f`) to regenerate regardless.

Only the spec's content is compared — changing `generator_name`, `openapi_generator_version` or
`additional_properties` without touching the spec will *not* trigger a rebuild on its own; use
`--force` after such a config change.

## Namespace conflict detection

Before registering a client's autoload mapping, generate-client checks whether a package already
required by the project (a real `vendor/` dependency) declares the same PHP namespace (PSR-4
root) — which would otherwise cause an autoload collision between that package and the generated
client.

If a conflict is found, you'll see a warning and be asked whether to abort or remove the other
package (via `composer remove`) so the generated client can be autoloaded instead. In a
non-interactive run (`--no-interaction`, e.g. in CI), it defaults to aborting.

## Auto-regeneration on every install

The first time `generate-client` runs, it adds itself to your project's `composer.json`:

```json
"scripts": {
    "post-install-cmd": ["@php vendor/bin/generate-client"],
    "post-update-cmd": ["@php vendor/bin/generate-client"]
}
```

(merged with whatever scripts you already have). From then on, every `composer install` or
`composer update` — on a teammate's machine, in CI, in a Docker build — regenerates any missing
or out-of-date client automatically. Combined with the spec-diff skip above, this stays fast:
an unrelated `composer require some/package` still re-runs generate-client, but it's a no-op
(sub-second) for every client whose spec hasn't changed.

## 2. (Optional) project-wide options via config/packages/

If your project follows the Symfony `config/packages/` convention, you can drop a
`config/packages/php_openapi_generator.yaml` file (copy
`vendor/jeandonaldroselin/php-openapi-generator/config/php_openapi_generator.dist.yaml`) to set the config
file path and other defaults instead of relying on the default `openapi-generator.json` location:

```yaml
php_openapi_generator:
    config_path: '%kernel.project_dir%/config/openapi-generator.json'
    cache_dir: 'var/openapi-generator/cache'
    generated_dir: 'var/openapi-generator/generated'
    java_binary: 'java'
    default_generator_version: '7.9.0'
```

This file is read directly (no Symfony kernel required), so it also works in a plain Composer
project that simply follows the same folder convention.

## 3. Run it

```bash
vendor/bin/generate-client
```

Useful options:

- `--config=path/to/file.json` — override the config file location for this run.
- `--client=billing` — only (re)generate one client from the config file.
- `--generator-version=7.10.0` — override the generator version for this run.
- `--skip-install` — only generate the code, without touching `composer.json` / running Composer.
- `--force-download` — re-download the generator jar even if a cached copy exists.
- `--force` (`-f`) — regenerate even if the spec has not functionally changed since last run.
- `--no-scripts` — pass `--no-scripts` to the `composer remove` call this tool makes when
  resolving a namespace conflict (e.g. in a build stage where project scripts like `cache:clear`
  can't run yet).

After it runs, the client is available under its declared namespace, e.g.:

```php
use Acme\Billing\Client\Api\InvoicesApi;
```

## Docker / CI

Java is required wherever `composer install`/`update` runs for this project. If you want to keep
Java out of your final runtime image, use a multi-stage build: run `composer install` (which
triggers generation via the registered script) in a builder stage that has Java, then copy just
`vendor/` (and, if you `--no-dev`-prune the builder afterward, run that second `composer install
--no-dev --no-scripts` pass specifically with `--no-scripts` — otherwise the post-install-cmd
script would try to run after `vendor/bin/generate-client` has already been removed by the `--no-dev`
prune) into a Java-less final stage.
